# Known risks and recovery matrix

This is the current risk register for privileged or multi-authority operations.
Resolved defects belong in executable tests and the changelog; only unresolved
operational boundaries remain here.

| Operation | Remaining failure boundary | Safe retry and recovery |
|---|---|---|
| First-start setup | Pool creation is intentionally non-compensatable. A successful setup can later become `configuration-changed`, `state-drift`, or `complete-unverified` when the normalized plan, authority probes, or final preflight no longer match. The browser wizard is the primary interface; its CLI backend also accepts a bounded stdin-only secret payload for authorized recovery integrations. Browser and worker secret validation share one contract. | Inspect `nas-setup status` and the journal; the wizard and `prepare-first-start` report a blocking journal before passwords are submitted. Never alter the device list to bypass an interrupted run. Reconcile the failed authority, acknowledge manual recovery explicitly when required, and repeat password mutation only with the dedicated confirmation. Keep browser access working before starting setup; use the authorized recovery backend when repairing an interrupted workflow. |
| Browser bootstrap and locked boot | After setup, the locked Caddy surface is Authentik sign-in plus the `nas_admin`-gated `/unlock/` page and `nas-unlock-api`, a root process that receives the KeePass password. A compromised `nas_admin` session can submit password guesses, which KDBX key derivation and the API's single-flight backoff bound but do not prevent. Authentik runs on a per-boot key with the system-partition database, so an offline attacker can still read Authentik data. Browser unlock cannot replace the recovery plane when Authentik, the outpost, or activation fails. | Keep console, SSH recovery-key, or hardware KVM access available, and use a strong KeePass password (setup enforces a floor). Review `journalctl -t nas-unlock-api` for attempts. Repair failures with `sudo nas-secrets activate` from the out-of-band path; do not expose Cockpit or add a local-PAM browser exception while locked. |
| Authentik account apply | The planner, journal, read-back verification, and explicit password replay improve convergence, but an accepted password cannot be restored automatically and remote API mutations are still a saga. | Use the sanitized completed/pending plan, re-run structural reconciliation, and deliberately rotate any password whose final value is uncertain. |
| State export and restore | The profile-aware registry, writer quiesce, signed manifest, canonical restore plan, exact unit snapshot, rollback retention, and database comparison digest are not one atomic cross-application ZFS snapshot. Authority roots now have code-owned owner/group/mode policy for restore onto an empty host, and existing heterogeneous subpaths preserve their observed local policy. The generic bundle still does not reproduce every ACL, xattr, capability, hard-link, sparse-file, or application-native database/filesystem semantic, and absent heterogeneous subpaths still require authority-specific restore policy. Raw mutable application/VM trees therefore remain higher risk than service-native backup or ZFS snapshot/send. The HMAC is appliance-secret trust, not a portable public signature. | Preserve KeePass and the bundle signing key through independent recovery media. Prefer service-native backup or ZFS snapshots/send for application and VM storage where available. Validate, diff, and inspect snapshot metadata before restore. Stop or isolate any external writer not included in the generated quiesce set. |
| Syncthing reconcile | Desired state is journaled and owned objects are read back before commit, but Syncthing does not expose one transaction spanning every device and folder mutation. | Re-run reconciliation to converge the prepared generation. Escalate only when an unmanaged object conflicts with a reserved managed identifier. |
| Cockpit operations | One kernel flock serializes privileged mutations. First-start admission is non-binding: its systemd worker must acquire the lock when it starts and can fail if another mutation wins the handoff race. First-start is a detached systemd job with reconnect-safe journal progress; a common cancellation protocol is still not available for every systemd job. | Reload Cockpit and inspect active operation metadata plus the durable setup/update journal. Retry a busy handoff after the active mutation finishes. Cancel only through a workflow-specific recovery path; killing the browser does not cancel the operation. |
| Cockpit protected restart | Restart protected services runs `nas-protected-restart.service`, whose worker owns the flock for the whole restart. The restarted target includes Caddy, which carries the Cockpit session, so the browser can lose its transport before the synchronous result arrives. | Reload Cockpit and inspect `nas-protected-restart.service` for the result. |
| Established Cockpit sessions | Caddy checks Authentik and the V2 console capability on HTTP requests, including WebSocket upgrades. The shared privileged bridge does not reauthorize subsequent messages. Group revocation, account disablement, and Authentik logout do not alone terminate an established connection; there is no configured stream lifetime or per-user transport revocation. | Revoke the unwanted grants and Authentik sessions, then restart `nas-cockpit-sso.service` from console or authorized SSH. This disconnects all console users. Verify fresh access is denied and review independently launched work. A connection lifetime/revocation policy and installed end-to-end qualification remain open. |
| Applications sharing the management origin | V2 path exposures place application scripts on the same browser origin as Cockpit and Authentik. Capability checks restrict requests but do not isolate scripts by URL path; cross-origin response headers do not create separate origins within one hostname. | Treat applications on that origin as trusted browser code. Use separate V2 hostname exposures for applications needing a distinct browser trust boundary. Test login, cookie, origin, and CSRF behavior across the deployed hostnames. |
| V2 capability removal | Removing a declared capability or service generates deletion of its Authentik capability group. That deletion also removes Authentik-owned membership relationships. A later V2 rollback can recreate the group but cannot reconstruct its prior memberships, because the compiler never stores or assigns human grants. | Disable a service for a temporary stop; its declared groups and memberships remain. Before removing declarations, preserve the required Authentik backup and review assignments. Regrant access in Authentik after a rollback that recreated deleted groups. Membership-preserving deletion/compensation needs a separately qualified contract. |
| Generic Managed Services jobs | Generated exec/Python job owners do not infer appliance mutation classes or acquire the appliance flock. Cockpit's `runtime` conflict display is advisory. The seeded appliance jobs use existing systemd owners, whose command-level coordination remains separate from generic workload projection. | Identify commands that mutate shared appliance state and use the existing coordinator inside those workers for their full lifetime, with nested token/class validation. Do not hold the HTTP caller's flock across systemd launch or blanket-lock arbitrary workloads. A generic policy and affected-owner/NixOS qualification remain open. |
| Secret activation | Swap rollback is phase-aware and checked, but a failed protected-stack restart after restoring the prior tree still requires operator intervention. | Keep the previous tree, inspect the correlated journal entries, repair the failed unit, then restart `nas-protected-services.target` or reactivate secrets. |
| Backup independence | `nas-backup-status` classifies where the configured repository is, not whether it is physically independent. A network backend could point back at this host, a local path's disk may be unmounted at boot (it then resolves to the system disk, which status reports but readiness does not reject), and a successful restore verification restores on this host. | Treat the Cockpit backup card as configured/completed/verified observations only. Prove independent restore with the boot-device replacement drill before relying on it. |
| Update deployment | Candidate source, mutable-state snapshot, Nix generation, and rollback evidence are recorded, but a database migration may not be safely downgradeable and local health does not prove second-host reachability. | Use NanoKVM or another out-of-band path, inspect the manual-recovery marker, and restore application state only under the documented compatibility policy with all writers stopped. |
| Network/firewall state restore | Changed network state requires explicit CLI disconnection acknowledgement before mutation. Unchanged network files/services are preserved during unrelated restores. Restoring changed NetworkManager/firewalld state can still sever remote administration; there is no independent timed-confirmation rollback yet. | Perform network-affecting restore with NanoKVM/out-of-band access until a timed remote-confirmation rollback contract is implemented and VM-tested. |
| NVIDIA GPU CDI naming | The probe prefers the driver UUID name but falls back to the toolkit index name when no UUID is resolvable or the provider publishes index names only. On a host with non-contiguous driver minors that fallback can name a different GPU than `/dev/nvidiaN`; the device selector still identifies the right card. | Reconcile once the driver exposes `/proc/driver/nvidia/gpus`, confirm `nvidia-ctk cdi list` publishes the UUID strategy, then redeclare or restart the affected service. See [ADR-0002](adr-0002-nvidia-cdi-device-names.md). |
| Direct storage lifecycle mutations | Setup/state/update/identity/feature/secret paths now share the operation coordinator, but systemd-owned ZFS lifecycle helpers still require runtime proof before being wrapped because naïve nesting can deadlock protected-target startup. | Treat overlapping manual storage lifecycle operations as unsupported until the native/QEMU service-ordering tests prove a coordinator-safe integration. |
| OCI application isolation | V2 projects persistent OCI apps as system-level Quadlet units, which run rootful with container UID 0. Installed checks restrict inspection to non-privileged, read-only root, no added capabilities or host PID sharing, no Podman socket, one isolated network and only declared bind mounts; they also verify seccomp, no-new-privileges and capability equality. That is not user-namespace or rootless isolation, and no such profile is claimed. | Do not run untrusted code in a V2 OCI app until a rootless or equivalent profile is qualified. Never mount the Podman socket, host devices, or host display/input sockets to work around it; track the remaining work in #141. |

## First-start recovery

Preexisting Managed Services history with desired revisions but no applied ref
remains a manual-recovery boundary, including partial baselines left by older
bootstrap code. Commit contents alone cannot establish prior successful apply.
See [Missing applied configuration history](../src/admin/maintenance.md#missing-applied-configuration-history).

Failed first-start identity regeneration intentionally leaves its discovered
identity/Syncthing timers stopped. Their prior active state is not persisted
across a failed worker; manual recovery must restore the previously active
timers after repairing the identity stack and completing setup. Timer names
are recorded in the worker journal. See [First start](../src/admin/first-run.md).

## Required external evidence

Authentik's source package supplies a per-response nonce CSP and CSSOM frontend
bindings; both public proxy configurations emit cross-origin isolation headers.
Those headers do not split path-based applications into separate browser origins.
These repairs require installed browser/API, CSRF/session and accessibility
qualification, including Lit's nonce-bearing stylesheet fallback. External
branding/assets cannot rely on wildcard image or inline script/style allowances.
ZAP qualification remains unresolved until complete installed scans pass without
breaking upstream authentication/application interfaces.
The packaged scanner keeps the known informational cache/application/session
rules visible as `INFO`; every unclassified warning and security failure remains
fatal.

A source-only release is not hardware evidence. Nix evaluation, closure builds,
the native NixOS tests, evaluated service-user ownership tests, the official-ISO
install/reboot harness, firewall behavior, and applicable live drills must pass
before an install-ready designation.
